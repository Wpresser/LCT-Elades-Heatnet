# Сервис моделирования трасс подключения к тепловым сетям — описание решения

ЛЦТ 2026, задача 2. Сопроводительная документация (раздел 5 основного ТЗ). Правила расчёта —
по актуальному техническому приложению и письменным разъяснениям; решение по спорному правилу конечного участка — в `TERMINAL_POLICY_DECISION.md`.

## 1. Что делает сервис

Получает один GeoJSON (WGS 84) с существующей тепловой сетью, камерами, источником, точками подключения ОКС
и пространственными ограничениями. За один запуск строит два содержательно разных варианта новой сети
(по желанию — третий, базовую линию «каждая цель отдельно»)
в двумерном режиме, рассчитывает расходы, условные диаметры, стоимость и итоговый показатель S, ранжирует варианты
и выгружает результат в GeoJSON по разделу 7 технического приложения.

Режим с учётом глубины не реализован (необязательный, приложение §5): `depth_start` и `depth_end` = `null`,
Kгл = 1. Реконструкция существующей сети и камер и её расходы не рассчитываются: приложение §2.4 прямо исключает
их из расчётной модели, разъяснения №14 и №16 это подтверждают (в исходной редакции приложения от 10.09 они были).

```
POST /api/jobs ──► файл на диск (поток) ──► очередь расчётов ──► чтение в два прохода
                                                                   │
        GET /api/jobs/{id}/result ◄── GeoJSON ◄── ранжирование ◄── варианты v1, v2 (v3 — по желанию)
```

## 2. Подготовка данных

1. **Потоковое чтение.** Файл читается по одному объекту Feature (Jackson streaming) в два прохода:
   сначала источник, сеть, камеры и точки подключения; затем только те ограничения, чей охват попадает
   в окна поиска вокруг целей. Идентификаторы сохраняют тип (строка или число).
2. **Проекция.** Все длины, расстояния и габариты считаются в EPSG:32637 (UTM 37N); перевод сверен с PROJ.
3. **Окна поиска.** Вокруг каждой цели — квадрат радиусом max(300 м; 1,5 · расстояние до сети + 150 м).
   Трасса не выходит за объединение окон: за его пределами ограничения не загружены. Если цель не подключилась,
   расчёт повторяется с окнами в 2,5 раза больше.
4. **Топология существующей сети.** Для каждой камеры считаются примыкания: конец линии — 1, проходящая линия — 2
   (приложение §2.1). Проверяется связность сети и положение источника.

## 3. Поиск трассы одной цели

**Препятствия.** Для выбранного ДУ каждое запретное ограничение (ОКС, парк, территория соцобъекта, запретная
территория, водный объект, железная дорога) расширяется на «отступ по таблице 2 + ½ ширины пары» — ось трассы
в эту зону не заходит, значит, внешний габарит трубы выдерживает отступ. Объекты со спецпроходом (дороги,
трамвай, газопровод, кабель, существующая теплосеть) образуют зоны, в которые можно войти только допустимым
спецпроходом.

**Граф видимости.** Вершины — выпуклые углы расширенных препятствий. Рёбра — прямые отрезки между вершинами,
не задевающие запретных зон. Для каждого ребра проверяются пересечения со спецобъектами:

- пересечение одно, полностью (вход и выход);
- для дорог и трамвая угол к границе не меньше 45°;
- спецучасток — прямой, покрывает объект и запас по таблице 2 (полигон + 3 м, точка пересечения ± 2 м),
  а также всю зону отступа вокруг пересечения (см. `TERMINAL_POLICY_DECISION.md` и официальные документы в `task/`);
- при наложении спецпроходов участок делится на границах смены набора ограничений, Kспец — наибольший.

**Поиск.** A* по состояниям «(предыдущая вершина, текущая вершина)» — это позволяет точно соблюдать поворот
не более 90° в каждой вершине (приложение §2.1). Цена ребра — его вклад в итоговый показатель:
0,7 · стоимость / 25 млн + 0,3 · длина / 100, поэтому поиск сразу учитывает Kспец и стоимость камер.
После поиска трасса выпрямляется: вершина убирается, если прямой отрезок между соседями допустим.

**Подход к зданию (приложение §2.2).** Точка подключения лежит внутри полигона своего ОКС. Если она на контуре
или снаружи не дальше 0,5 м (ТЗ §1.1: «точку подключения на границе ОКС»), для расчёта она сдвигается на 5 см
внутрь своего здания по нормали к ближайшей стене. В выгрузке остаются исходные координаты, сдвиг отражён в
замечаниях к входу. Финальный прямой
участок идёт от цели через ближайшую точку внешнего контура наружу, до выхода из зоны отступа; отступ к своему
ОКС на нём не действует, остальные ограничения — действуют. Если такой выход невозможен по входным данным
(ступенчатый фасад, внутренний двор), берётся ближайшая точка контура со свободным выходом. Каждая цель, чей
финальный участок проходит не через глобально ближайшую точку границы (включая стены дворов), перечислена
в `diag_relaxed_final_approach` и в блоке интерфейса «Трактовки и отступления»
(см. официальные документы в `task/` и решение по правилу в `TERMINAL_POLICY_DECISION.md`).

**Место присоединения (приложение §2.4).** Кандидаты: основание перпендикуляра на ближайших трубах и точки со
сдвигом вдоль трубы; существующие камеры с запасом примыканий. Если точка ближе 10 м к существующей камере,
у которой после подключения будет не больше четырёх примыканий, используется эта камера. Иначе на трубе
ставится новая камера. Стоимость новой камеры — по наибольшему ДУ примыкающих участков, включая существующую
трубу (см. официальные разъяснения в `task/`); врезка в существующую камеру — 5 млн руб. за каждый участок.

## 4. Совместное подключение и варианты

Цели обрабатываются по очереди (порядки — ниже). Каждая присоединяется туда, где дешевле по показателю S:

- к существующей сети (новая камера на трубе или существующая камера);
- к уже построенной новой сети — новой камерой на участке (разветвление) или в существующую новую камеру.
  В цену входит камера и удорожание общего участка до присоединения из-за роста расхода.

После каждого присоединения по всему дереву пересчитываются расходы (сумма flow_tph ниже по течению) и ДУ:
минимальный по расходу, неизменный на цепочке с постоянным расходом, не убывающий к присоединению; если
непрерывный путь одного ДУ длиннее предельной длины таблицы 1, верхняя цепочка пути берёт следующий ДУ.
Трассы совместной сети прокладываются с габаритом ДУ суммарного расхода, поэтому рост ДУ на общих участках
не нарушает отступов; если всё же нарушает — присоединение откатывается, и цель подключается иначе.

| Вариант | Как строится |
|---|---|
| v1 | совместное подключение: цель выбирает между существующей и новой сетью по цене |
| v2 | минимум присоединений к существующей сети: после первой цели сначала только ветки новой сети (меньше присоединений, чем у v1) |
| v3 | каждая цель отдельно — базовая линия для сравнения, выдаётся только при `HEATNET_SEPARATE_VARIANT=true`. Трассы обходят друг друга; если отдельная трасса невозможна, цель присоединяется к уже построенной сети (приложение §2.5) |

Совместная сеть зависит от порядка обработки целей, поэтому пробуются три порядка (ближе к сети — раньше;
больший расход — раньше; ближайшая к уже подключённым) — всегда все три, чтобы результат не зависел от скорости
стенда, — и берётся лучший по S. Затем каждая цель по очереди снимается
вместе со своей веткой и присоединяется заново при готовой остальной сети — изменение остаётся, если S уменьшился.

Если после присоединения ДУ общего участка вырос сверх габарита, с которым участок проложен, цепочка участков
между узлами смены расхода прокладывается заново с новым ДУ; если не получается — присоединение откатывается.

Варианты ранжируются по S = 0,7 · C / 25 000 000 + 0,3 · L / 100 (меньше — лучше).

Результат на конкурсном наборе (17 целей):

| Вариант | Подключено | Длина, м | Стоимость, млн руб. | S |
|---|---|---:|---:|---:|
| v1 (strict/literal, default) | 14/17 | 1 553,652 | 568,862 | 20,589 |
| v2 (strict/literal) | 14/17 | 1 805,682 | 595,418 | 22,089 |

Strict output содержит `unconnected_oks_ids = [2, 5, 10]`. Отдельно сохранён alternative/relaxed output: v1 = 17/17, 1 824,673 м, 271,516 млн руб., S = 13,076; v2 = 17/17, 2 078,298 м, 289,678 млн руб., S = 14,346. Alternative не используется как официальный strict результат и всегда сопровождается disclosure.

## 5. Если маршрут не найден

Цель без найденной трассы не мешает остальным: частичный результат сохраняется, её id попадает
в `unconnected_oks_ids` варианта, начисляется штраф 100 000 000 + 500 000 · flow_tph (приложение §6).
Причина пишется в `diag_unconnected_reasons` сводки. Намеренного отказа от подключения ради показателя нет:
цель остаётся неподключённой, только если поиск не нашёл допустимой трассы (приложение §2.5, разъяснение №15).
Отсутствие найденного маршрута не доказывает, что подключение физически невозможно. Точка подключения без
корректного `flow_tph` не теряется: она тоже в `unconnected_oks_ids` с причиной (штраф посчитан с расходом 0),
а в замечаниях к входным данным — пояснение.

## 6. Выходные данные

GeoJSON FeatureCollection в WGS 84, варианты различаются `variant_id` (приложение §7):

| object_type | Геометрия | Основные атрибуты |
|---|---|---|
| heat_network | LineString | start_node_id, end_node_id, flow_tph, diameter, length, laying_method, depth_start/end = null, cost |
| heat_chamber | Point | diameter, cost (новые камеры) |
| technical_node | Point | — (границы спецпроходов) |
| variant_summary | null | rank, construction_cost, chamber_construction_cost, existing_chamber_tie_in_count/cost, unconnected_penalty, calculated_cost, new_network_length, score, unconnected_oks_ids |

ДУ и стоимость новой камеры — по наибольшему ДУ всех примыкающих к ней участков, включая существующую трубу,
на которой стоит камера присоединения (приложение §3.2 «всех примыкающих участков»). Это консервативно: стоимость
не занижается. Сравнение стоимости только новых участков относится к диагностике и не меняет финальные strict KPI;
спорные трактовки и их отдельные метрики приведены в `docs/TERMINAL_POLICY_DECISION.md`.

Дополнительные поля с префиксом `diag_` — пояснения, при проверке обязательной части они игнорируются:

| поле | где | что значит |
|---|---|---|
| `diag_dn_by_flow` | участок | минимальный ДУ по расходу; если `diameter` больше — ДУ повышен правилом предельной длины |
| `diag_k_spec`, `diag_crossing` | спецучасток | Kспец и что пересекается |
| `diag_tie_in` | новая камера | камера на существующей трубе (присоединение) |
| `diag_description` | сводка | как построен вариант, какой порядок целей выбран |
| `diag_terminal_policy` | сводка | трактовка §2.2 (`literal` / `exterior` / `relaxed`) |
| `diag_relaxed_final_approach` | сводка | цели, чей финальный участок не через глобально ближайшую точку границы |
| `diag_unconnected_reasons` | сводка | причина неподключения по каждой цели |
| `diag_search_truncated` | сводка | перебор прерван страховочным лимитом времени (на конкурсном наборе — нет) |

Концы участков совпадают с узлами: для объектов входа пишутся их исходные координаты. Числа пишутся без
экспоненты. Точки врезки (разъяснение №13: объект `tie_in` не формируется) — новые камеры с `diag_tie_in = true`
и существующие камеры, на которые ссылаются `start_node_id`/`end_node_id` участков.

## 7. Нормативная база и расхождения документов

Реализованы техническое приложение ред. 18.09 (`task/sources/Техническое  приложение ЛЦТ.docx`) и разъяснения
№1–17. Разъяснение №16: при расхождении правил применяется актуальное техническое приложение; разъяснение №17:
структура входа определяется им же. Основное ТЗ (`2. ДИТ.pdf`) датировано 13.09, то есть написано раньше актуального
приложения.

| положение ТЗ или исходной редакции приложения (10.09) | актуальное правило | что делает сервис |
|---|---|---|
| реконструкция существующей сети и камер, расход к источнику (ТЗ §2.10–2.11, §4 п. 4 и 6) | не выполняется (приложение §2.4, разъяснение №14) | не рассчитывает; справочно — добавленный расход по существующей сети (`results/checks/`) |
| объект `tie_in` в выгрузке | не формируется, присоединение — через `heat_chamber` (разъяснение №13) | точки врезки — камеры с `diag_tie_in = true` и существующие камеры, на которые ссылаются `start_node_id`/`end_node_id` |
| `oks_future` / `oks_existing`, `oks_id`, `upstream_object_id` | здания — `restriction` c `restriction_type = oks`; расход — у точки подключения | принимает оба формата |
| режим с глубиной | необязателен (разъяснение №16) | не реализован, `depth_start/end = null` |
| поля сводки `reconstruction_cost`, `tie_in_cost`, `length` | в §7 их нет | не выдаются |

Где выбрана трактовка (приложение её не уточняет), это раскрыто в выгрузке и в интерфейсе, в блоке «Трактовки
и отступления»:
- §2.2, точки 2, 5, 10;
- граница спецучастка и отступ;
- ДУ камеры на существующей трубе.

## 8. Границы применения

- Только двумерный режим; вертикальные требования таблицы 2 не проверяются.
- Реконструкция и пропускная способность существующей сети не рассчитываются (по актуальному приложению).
- Поиск эвристический: оптимальность глобально не гарантируется. Порядок обработки целей влияет на результат.
- Трасса строится внутри окон поиска вокруг целей; очень далёкие обходы не рассматриваются.
- Спорные места ТЗ (граница спецучастка и отступ, нестрогий финальный подход, стоимость камеры по ДУ
  существующей трубы) решены по трактовкам из `TERMINAL_POLICY_DECISION.md` и официальных документов в `task/`.
- Производительность (`results/load_test/`):
  - конкурсный набор — около 47 с на ноутбуке;
  - файл 3,00 ГБ (9,9 млн объектов) — загрузка 53 с, чтение 3 мин 35 с, расчёт 1 мин 26 с, пик памяти процесса
    626 МБ при heap 1 ГБ;
  - 50 одновременных клиентов — 550 из 550 запросов, задержка до 0,95 с; расчёты идут в очереди (в docker-compose —
    по два одновременно).
  - Тысячи целей в одном файле не проверялись.
